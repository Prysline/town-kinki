# TOWN 繁體中文 Web 移植計畫

這是與原始 Perl/CGI 並行的 **Web 移植雛形（第 30 階段持續開發）**。原始檔案保留在儲存庫根目錄，Web 程式獨立放在 `web/`，不會覆寫原版遊戲。

> **分支與驗收邊界**：原版 Perl/CGI 保留在 `master`，Web 開發及盤點合併到 [`feature/web-dual-mode-phase1`](https://github.com/Prysline/town-kinki/tree/feature/web-dual-mode-phase1)；**最新合併 PR 與 CI 狀態請查 [GitHub PR](https://github.com/Prysline/town-kinki/pulls?q=is%3Apr+is%3Amerged) 及 [Actions](https://github.com/Prysline/town-kinki/actions)**，不在此維護容易過時的「最新 PR 編號」。目前局部成果包括原版 BMI 職業門檻、捨入邊界、體格摘要、原版已匯入圖示手動預覽、來源盤點及美容物品測試；**不代表整個原版遊戲、真實玩家存檔或瀏覽器視覺驗收完成**。

> **第 30 階段盤點與後續工作**：[最新待辦總清冊：未深入盤點／已盤點未修／已修待驗收](docs/phase30-open-audit-backlog.md)、[現行原版 → Web 差異矩陣](docs/migration-audit.md)、[全 43 個原版地圖互動入口與 Web 導覽覆蓋表](docs/phase30-entrypoint-coverage.md)、[外貌與圖示來源](docs/appearance-source-audit.md)、[職業／教室／公開個人檔案](docs/phase30-jobs-training-profile-audit.md) 分別追溯原版程式與實際缺漏。**現有 CI 只核對入口清單／圖示，並不逐子 CGI 驗證功能**；歷史 [工作契約](docs/PHASE30-MIGRATION-INVENTORY-PLAN.md) 不是驗收證明。實際玩家資料／瀏覽器仍待驗收。

## 環境

需要 **Node.js 22.13 以上**，使用內建 `node:sqlite`（此功能在 Node.js 22 仍會顯示實驗性功能警告）。不需要外部 npm 套件。

```sh
cd web
npm test
npm start
```

預設進入單機模式，開啟 http://127.0.0.1:3000 即可建立角色。資料存於 `web/data/solo.sqlite`，瀏覽器清除 Cookie 不會刪除本機角色。

多人模式：

```sh
cd web
GAME_MODE=multi HOST=127.0.0.1 PORT=3000 npm start
```

接著在同一個地址開啟網站，各玩家可以分別註冊帳號。若需供其他裝置連線，請在可信任的 HTTPS 反向代理後部署，設定 `HOST=0.0.0.0`、`COOKIE_SECURE=1`。目前尚無登入速率限制、正式部署安全審查及備份管理，**不建議直接公開至網際網路**。

Windows PowerShell 可使用：

```powershell
cd web
$env:GAME_MODE = "multi"
npm start
```

單機與多人資料庫**彼此獨立**，但使用相同的規則、資料結構與前端介面。目前不支援兩者之間自動同步或轉移角色。

## 第二十七階段補充：單人刪除角色並重新開始

在單人模式的遊戲畫面按頂部 **「離開遊戲」**，回到城鎮首頁後可在 **「刪除角色並重新開始」** 展開區域操作：

1. 畫面顯示目前角色名稱與不可恢復警告。
2. 玩家須**手動輸入完整角色名稱**，再勾選「瞭解永久刪除」。
3. 按「永久刪除角色」後還有一次瀏覽器確認視窗；取消時沒有任何變更。
4. 確認成功後直接回到建立新角色介面。可以重新使用之前的角色名稱。

`POST /api/solo/character/delete` 僅限 `GAME_MODE=solo` 使用，傳入 JSON 物件 `{"characterName":"完整角色名稱","confirm":true}`。伺服器比對目前 SQLite 裡真正的角色名稱，拒絕名稱不符、缺少確認或無角色的要求；多人帳號無權使用這個 API。

**刪除範圍與保留範圍分開：**

- **永久刪除：** 單機本機玩家目前角色與所屬金錢、能力、職業、住宅權屬、銀行／貸款／交易、背包／原始物品封存、住宅室內配置與留言、事件紀錄／獎勵／限時挑戰、匯入角色／物品映射，以及其餘以此單機玩家為所有者的資料。透過 `users` 的 SQLite `ON DELETE CASCADE` 一次清除，之後自動建立空白單機帳號，**不會建立新角色**。
- **保留：** 四座城鎮 `town_maps`（包含玩家自行配置的道路、設施及其他非住宅格子）、單人遊戲時間 `solo_clock` 的偏移量和原始遊戲素材。玩家自己建造的房屋所占格子只還原成建造前的原始空地種類，避免留下無人擁有的 `webhouse_...` 地圖符號。
- **不含：** 整個世界重置、全資料庫清除或多人帳號刪除；這些是不同操作，本功能沒有實作。

刪除前先比對每一棟住宅記錄與當前地圖格子，透過 SQLite `BEGIN IMMEDIATE` 在**同一筆交易**內還原住宅格子並清除角色資料；若資料異常則全面回滾，不會清除到一半。測試包含有住宅、留言、銀行、背包、事件的角色、錯誤名稱、未確認、多人的拒絕、故意破壞地圖後回滾、城鎮地圖與單機時間保留，以及刪除後重新建立同名角色。

## 第二十七階段補充：單機返回首頁與遊戲時間快轉

原本 `web/public/app.js` 只在多人模式顯示頂部 `#logout`，單人模式雖然自動使用本機居民，卻沒有「離開遊戲」入口。本階段將此流程明確區分：

- **多人模式：** 顯示「登出」，執行現有 `POST /api/logout` 清除伺服器 session cookie，返回登入畫面；既有認證規則維持不變。
- **單人模式：** 顯示「離開遊戲」，僅返回「城鎮預覽＋繼續遊戲」首頁，不移除資料庫角色、不登出不存在的帳號，也不刪除任何存檔。首頁的「繼續遊戲」恢復角色操作；停留首頁的狀態以瀏覽器 `sessionStorage` 保存，可跨同一分頁重新整理。單機模式不需要密碼。

### 快轉操作與等待來源

單人角色摘要中增加四個伺服器驗證的預設快轉按鈕：

| 按鈕 | 伺服器推進時間 | 對應實際遊玩等待 |
|---|---:|---|
| ＋5 分鐘 | 300,000ms | 工作冷卻 5 分鐘（`WORK_COOLDOWN_MS`） |
| ＋30 分鐘 | 1,800,000ms | 體力／腦力每 10 秒恢復、健身房按課程冷卻 |
| ＋1 小時 | 3,600,000ms | 用餐最短間隔 60 分鐘（`MEAL_COOLDOWN_MS`） |
| ＋1 天 | 86,400,000ms | 學校每日一堂課、隔日狀態及銀行每日結算 |

*此功能只在 `GAME_MODE=solo` 提供。* `POST /api/solo/time/advance` 僅接受 JSON `{"preset":"5m"|"30m"|"1h"|"1d"}` 中的單一字串，其他輸入拒絕；多人模式登入者回傳 HTTP 403、未登入者仍維持 401，尚未建立角色時回傳 409。時間無倒退功能，累計快轉上限為 10 年。

虛擬遊戲時間以 `solo.sqlite` 的 `solo_clock.offset_ms` 持久化；重啟伺服器後保留。單人模式的工作、能量恢復、學校／健身房、用餐、銀行、貸款、健康／每日事件、健康保險、道具冷卻、住宅紀錄及留言時間都依同一伺服器遊戲時鐘計算。多人模式、登入／註冊／工作階段失效仍使用真正的伺服器時間。

**快轉不是讓伺服器逐秒執行模擬：** 選擇「＋1 天」直接推進遊戲時鐘 24 小時，下一次快照會依既有 Web 規則對新的遊戲日做一次結算與事件檢查；若跨過多個日期，不補算每個跳過日的利息、事件或薪資。若有仍在 20 秒時效內的蟑螂挑戰，伺服器拒絕快轉，以避免無意跳過限時事件。頁面時鐘與事件倒數使用伺服器回傳的遊戲時間校準，不會因本機時鐘和遊戲時間偏移而出錯。

測試包含：四個預設步長與非法輸入、SQLite 關閉重開後偏移不遺失、工作／用餐冷卻實際解鎖、跨日及多人限制、進行中事件保護、單人返回與繼續遊戲的介面結構。

## 城鎮地圖與原版資料匯入

原始地圖不是圖片檔，而是 `log_dir/townlog0.cgi` 至 `townlog3.cgi` 中的一行 `<>` 分隔資料。每座城鎮使用 **12×16 格**，原始布局的 A1 位於第 22 欄（從 0 起算），L16 位於第 224 欄；其他城鎮名稱、人口、經濟與預留欄位不會在匯出時任意刪除。

**目前這份 fork 的四個 townlog 檔案全部為零位元組，沒有原始建築配置。** Web 版會正確顯示「尚未配置的空白街區」，不會擅自產生冒充原版的地圖。單機玩家可在網頁上開啟街區編輯模式，選用從原始 `unit.pl` 對應的設施與圖示；未識別的原始符號、居民建築會保留代碼並以待辨識狀態顯示。尚未匯入房屋詳細紀錄時，不會假造屋主或內部裝潢。

若有其他伺服器保存的原始 townlog 檔案，可在 `web/` 資料夾中匯入（指令需在同一資料庫使用者權限下執行）：

```sh
node scripts/town-map.mjs --town 0 --mode solo --import ../log_dir/townlog0.cgi
node scripts/town-map.mjs --town 0 --mode multi --import ../log_dir/townlog0.cgi
```

如果城鎮已配置，工具會拒絕覆蓋。確認備份後，才可明確加入 `--replace`。**若城鎮已有 Web 版住宅，即使指定 `--replace` 也會拒絕覆蓋，以免房屋與土地紀錄失聯。包含 Web 住宅的城鎮亦無法直接匯出至舊版格式，必須先完成房屋紀錄轉檔。**輸出會保留原版欄位結構，檔案文字編碼為 UTF-8。如果要將資料放回原始 CGI 伺服器，需先確認舊環境使用的日文編碼並進行轉換，不可直接假設 UTF-8 能被原版正確讀取：

```sh
node scripts/town-map.mjs --town 0 --mode solo --export ./town0-export.cgi
```

多人模式的地圖由伺服器共用，**不允許普通玩家透過 Web API 修改**。目前多人模式需透過伺服器端 CLI 匯入地圖；多人管理員編輯介面與進階設施互動尚未完成。一般住宅可由任何符合條件的已登入玩家在空地上建造。單機模式預設僅監聽本機回環位址，不應改成對外公開的未驗證編輯介面。

在匯入或編輯前請先備份 `web/data/`。此功能會新增 `town_maps` 資料表，不影響已建立的角色、工作或訓練資料。

## 住宅建造（第五階段）

1. 使用單機街區編輯器在當前城鎮配置「空地」、「空地（二）」、「商業用空地」或「商業用空地（二）」。多人模式需要由伺服器管理者預先匯入含空地的街區地圖。
2. 在街區地圖點選空地位置，再於建築公司選擇原版房屋外觀、室內 A 至 D 級，以及現金或銀行付款。
3. 頁面顯示按原始數據計算的地價、外觀費用和室內費用。**伺服器會重新計算全部費用，不採信瀏覽器提交的金額。**
4. 付款成功後，房屋與屋主登記於 `houses` 表，原始空地代碼保留在 `original_plot`，地圖顯示對應的房屋 GIF。房屋名稱可由屋主修改，其他玩家不能改名、重購或用地圖編輯器覆蓋。

原版城鎮地價分別為 **5,000 萬、2,000 萬、1,000 萬、500 萬圓**。例如和歌山島的 500 萬地價，加上 50 萬外觀與 D 級 100 萬室內費，總費用為 **650 萬圓**（6,500,000 元）。原版的 5 棟上限包含分店、運營公司與其他用途，因此目前 Web 版**只允許第一筆一般住宅**，不將尚未移植的後續建築類型假裝成一般住宅。這也意味著剛建立角色的 100,000 元初始現金不足以直接購屋，須先累積資金。原版的房屋分店倍數、各種企業建築、屋內完整商店／特殊功能與多人管理員工具尚未完成。

原始 `ori_ie_log.cgi`、玩家房屋 ID 與新 Web `houses` 並非同一套存檔。Web 版新建住宅使用專屬 `webhouse_` 代碼，避免與原版 ID 撞號；**含 Web 房屋的街區不可直接輸出回舊 CGI 使用**。本階段不會改寫任何原始 `log_dir/*.cgi` 檔案。

## 住宅出售與搬家（第六階段）

原版 `original_house.cgi`（`house_change` 與 `house_change2`）的規則是：**出售房屋時只退還該座城鎮的土地地價**，不退還房屋外觀、室內裝潢與建造時其他已支付費用。出售後，原本的格子會恢復為建造前的空地類型。

在 Web 版「我擁有的房屋」中，可看到出售退款金額並點選「出售住宅」，確認後會由伺服器重新計算退款。一次 SQLite 交易會完成：確認屋主、檢查街區與房屋紀錄一致、恢復原始空地、刪除房屋所有權、退還現金，以及寫入交易紀錄。如果任一環節失敗，所有變更會一併取消。

例如和歌山島建造一間外觀 50 萬、D 級室內 100 萬的房屋，花費 650 萬；出售時只退還 500 萬元的土地費。出售後可重新購屋，也可以換到其他城鎮建造。

住宅歷史記錄儲存在新增的 `house_events` 表，包含建屋與出售金額及時間。**更新前建立的 Web 住宅不會被虛構補登建屋紀錄**，仍可正常出售。為避免 SQLite 房屋編號重用導致舊出售請求意外作用於新屋，新建屋的編號會遞增超過目前房屋與歷史紀錄的最大編號。

仍未實作原版的全部屋內功能、分店與企業資產處理，因此目前只能出售在 Web 版建立的一般住宅。第七階段新增的室內內容設定與兩種留言板會在 Web 資料庫中依原屋主保存，出售不會轉交給新屋主；原版房屋檔案不會被這項功能修改。多人模式同時嘗試出售同一間住宅時，伺服器只會退款一次。

## 住宅室內設定與留言板（第七階段）

原始 `town_ini.cgi`、`original_house.cgi` 與 `town_lib.pl` 將 A 級、B 級、C 級與 D 級內裝分別對應 **4、3、2、1 個內容欄位**。原版每個欄位可設為一般留言板（代碼 `0`）、商店（`1`）、自訂網址（`2`）、屋主公告板（`3`）或不公開。此階段已支援一般留言板、屋主公告板、自訂網址的安全連結展示及不公開；**商店（代碼 `1`）尚無交易／庫存邏輯，因此不提供假功能或允許選取**。

建屋後，在「我擁有的房屋」點選「進入室內／設定」。屋主可以依室內等級配置欄位類型與標題；兩種留言板各自儲存文章，避免把屋主公告混入一般留言。單機與多人共用相同 API。多人訪客可在所在城鎮地圖點選有屋主的房屋，查看公開內容並在一般留言板發文；屋主公告板只能由屋主發文，但其他訪客可閱讀。未公開室內的住宅不允許訪客進入。留言能由原作者或屋主刪除。

原版自訂網址功能在 Web 版只提供 **HTTPS 外部連結**，不提供 HTML、嵌入式內容或任意腳本執行。所有留言透過純文字顯示，限制 250 字與同一作者在同一留言板至少五秒的發文間隔；這些長度與頻率防護是 Web 版新增的暫定限制，尚未主張與原 CGI 完全相同。

室內設定及留言是 **依角色帳號而非房屋編號**保存於新增的 `room_settings`、`room_posts` 表。當屋主出售房屋後，原本的設定與文章保留；重新購屋可繼續使用目前室內等級容許的欄位，升級與降級已可透過房屋改裝功能操作。新買家不會繼承原屋主的私人資料。舊 Web 存檔沒有室內資料時，系統會自動建立資料表並維持空白配置，**不虛構舊有的留言**。

原版自訂內容格式、玩家原始 `member/<ID>/oriie_settei.cgi` 及 `bbs1_log.cgi`／`gentei_log.cgi` 檔案尚未匯入，本階段仍不能直接輸出原版室內資料。公開部署前尚需要完整的帳號濫用、CSRF 及流量限制審查。

## 住宅外觀與室內改裝（第八階段）

原版 `original_house.cgi` 的 `house_change` 操作允許外觀與室內等級分別選擇新項目或維持現狀。**每項實際選擇改裝的費用採該項目完整原價**；同時改裝則相加。房屋所在土地無需再次購買，不收第二次地價，也不依已投入的舊外觀與裝潢費用折抵。與原版金錢欄位一致，Web 版目前**僅允許從現金支付改裝費**，不會自動動用銀行存款。

例如和歌山島既有 D 級住宅只更換為 `house/house_1.gif` 外觀，收費 160 萬元；只改為 A 級室內，收費 1,200 萬元；同時更換則收費 1,360 萬元。改裝完成後，房屋位置、土地標記、屋主與原始購入價格均維持不變。

操作方式：在「我擁有的房屋」使用「住宅改裝」表單，可單獨選擇新的外觀或室內等級。頁面提供外觀預覽與即時計算金額，確認後由伺服器再次計費。**僅屋主能改裝**。付款、修改房屋資料與寫入紀錄透過同一筆 SQLite 交易完成；金額不足、房屋不存在、街區與房屋紀錄不一致或多人競爭扣款時都不會產生部分修改。

室內 A／B／C／D 級對應的 4／3／2／1 欄內容仍遵守原版數量。降級只會隱藏超出新等級容量的欄位，**不刪除原屋主既有室內設定或留言**；日後重新升級時可再次顯示。若改裝的是外觀，室內不受影響。

為了不修改已存在的 `house_events` 表的 `built`／`sold` 型別限制，本階段新增 `house_remodel_events` 表保存改裝前後外觀、室內等級、費用、城鎮、位置與時間。更新既有 Web SQLite 時會自動建立新表，不覆蓋原有交易紀錄。改裝歷史不會推測或補造之前不存在的紀錄。

原版特殊城鎮價格倍率、特殊房屋圖示與一般住宅以外的附屬建物，尚未完全移植；本階段套用已解析且受支援的普通住宅外觀與室內標價。

## 銀行利息、超級定期與交易明細（第九階段）

原版 `basic.cgi` 明確寫出普通存款**每天一次 0.5% 利息**、超級定期**每天一次 1% 利息**、超級定期必須以**每 100 萬元為單位存入**，解約需要**全額取回**。原版 `town_lib.pl` 的 `kityou_syori` 將普通與定期的交易合計保留最多 **100 筆**。本階段已實作這些費率、單位與帳簿長度規則。

**計息時間的差異：** 已在原版 `town_maker.cgi::login_view` 確認，當 `access_time` 與當前日期不同時，會先計算普通與定期利息，再扣除當天貸款（以及後續的稅務）。Web 版目前採用：伺服器以 `GAME_TIMEZONE` 時區的日期判定，同一天第一次讀取已建立角色的狀態時，按當時的普通與定期餘額各自計息一次，利息採向下取整。當天任何後續狀態請求、存提款或玩家切換頁面不會重複計息。超過一天未讀取狀態時，下一次讀取**只計息一次，不逐日補發多次複利**。這仍是 Web 版以伺服器狀態讀取代替原版登入畫面的差異，並未移植後續稅務結算。

既有 Web 存檔首次啟動新版時，會在第一次讀取角色狀態時設定當天為利息起始日，不倒推累積過去沒啟用銀行系統的利息。此後每次跨日期計息，會同時記錄利息與更新餘額，交易期間若發生金額不足或其他錯誤，所有寫入都會回滾。

普通存款可繼續使用原有「存款／提款」介面。新增「超級定期存款」介面，輸入整數個 100 萬元單位來存入，解約只能一次將全部定期餘額退回**現金**，不提供部分提款。利息則加至各自帳戶的本金餘額。交易明細可篩選普通或定期，兩帳戶合計最多 100 筆，依時間由新到舊呈現。銀行存款用於支付 Web 版住宅建造時，會將支出記入普通帳簿。

模組位於 `src/banking.mjs`，使用新增的 `bank_accounts` 及 `bank_ledger` 兩張資料表。一般銀行存款仍保留在 `characters.bank`，不會搬移或重置已建立的餘額；超級定期使用獨立欄位。為避免 JavaScript 超過安全整數範圍的金額失真，利息以 `BigInt` 計算後才換算回可安全儲存的整數。

目前已支援多人玩家間轉帳與新的 Web 住宅貸款，但未移植原版既有貸款負債，也未匯入原版玩家的 `ginkoumeisai.cgi` 歷史紀錄。當前新增的交易明細僅代表 Web 版已實作的相關銀行操作，不會替先前版本的銀行操作虛構交易歷史。多人正式部署前仍須補齊安全審查。

## 銀行玩家間轉帳（第十階段）

原版 `basic.cgi` 的 `ginkoufurikomi` 與 `soukin_chc` 規則為：轉帳從**匯款人的普通存款**扣除，匯入**收款人的普通存款**；不可轉給自己；單次轉帳上限由 `hurikomijyougen` 設為 **1,000,000,000,000 元（1 兆元）**；在 `itinitiseigen = 'yes'` 時，每天對同一收款人的累計轉帳金額也不能超過上限。收款角色首次存取未滿七天時，**單筆滿 1,000,000 元即拒絕**。這些條件目前均有實作。

**與原版不同的超額處理：** 原版設定 `soukingaku_over = 'no'`，轉帳超過上限時，多出的部分會當成捐款，仍從匯款人普通存款扣除。Web 版**不自動捐出超額部分，直接拒絕超額轉帳**，避免使用者意外損失。多人模式銀行介面要求填寫**收款角色名稱**及金額，送出前顯示確認視窗。單機模式沒有其他玩家，因而不開放跨玩家匯款。

原版七天限制所依據的是角色存檔中的 `first_access`，不是帳號註冊日期。本階段新增 `characters.created_at` 儲存**角色建立時刻**，作為 Web 版七天規則依據。舊 Web 角色沒有可驗證的首次建立日期，因此遷移後欄位保留 `0`，將其視為既有角色，不猜測其年資、不重置角色資料。

匯款由 SQLite 的單筆 `BEGIN IMMEDIATE` 交易執行，包含確認收款人、驗證同日限額與餘額、按當日原有餘額結算收款雙方利息、從匯款人普通帳戶扣款、向收款人普通帳戶入帳、雙方帳簿記載以及保存轉帳稽核紀錄。若任何條件不成立，**所有銀行異動及當次觸發的計息也會回滾**。收款人的本日利息在收到新轉入款項之前結算，避免首次查看餘額時對當天剛收到的款項重複給息。

新增 `bank_transfers` 表保存匯款人、收款人、日期與金額，讓每日累計限額不會因銀行通帳只保留最近 100 筆而失效。每次前端轉帳均附唯一識別碼，同一識別碼與同一內容重送時回傳先前交易編號，**不再扣款**；若重用識別碼卻修改收款人或金額，伺服器會拒絕。此機制為 Web 版新增的安全保護。

銀行轉帳目前只處理同一多人伺服器內已建立角色的玩家，無法轉給不存在的角色、單機角色或其他伺服器。原版的特殊管理員轉帳與上限超額捐款仍未移植；貸款已移植基礎流程，但負存款及原角色貸款資料轉入仍有差異。

## 原版角色存檔預覽與離線匯入（第十一階段）

本階段依 `town_lib.pl` 的 `kozin_sprit` 定義解析 **69 個原版欄位**，支援讀取原始 `member/<ID>/log.cgi` 單筆角色紀錄，或以 `--id` 從多筆 `log_dir/memberlog.cgi` 指定角色。工具支援 UTF-8 與 Shift_JIS 編碼，不執行 CGI 原始碼。這個 fork 中的 `log_dir/memberlog.cgi` 是空檔案，因此無法提供真實玩家資料；需要使用者自行提供曾經運作的原版伺服器備份。

### 先預覽，不修改資料庫

在 `web/` 資料夾執行：

```sh
node scripts/legacy-character.mjs --file ../member/42/log.cgi --preview
node scripts/legacy-character.mjs --file ../log_dir/memberlog.cgi --id 42 --preview
```

預覽會顯示原始 ID、角色名稱、能力值、現金、普通與定期存款、職業對應、尚未支援的資料及轉檔警告，**不印出原版密碼**，亦不建立資料庫或備份。可用 `--name 新名稱` 處理原版名稱不符合 Web 格式的角色。預覽示例路徑須替換為實際存檔檔案；這個 fork 沒有可直接匯入的有效範例。

### 正式匯入

請先備份 `web/data/`，使用 `npm start` 初始化單機或多人資料庫後關閉伺服器，再進行匯入。正式匯入需要 **`--apply --accept-partial`**，確認目前只移植一部分原版系統。

單機模式只允許填入尚未建立角色的本機帳號，已有角色時**拒絕覆蓋**：

```sh
node scripts/legacy-character.mjs --file ../member/42/log.cgi --mode solo --apply --accept-partial
```

多人模式必須指定新帳號並另設**全新的登入密碼**，不能沿用原版 CGI 的密碼。先在執行環境中設定 `TOWN_IMPORT_PASSWORD`，再執行：

```sh
node scripts/legacy-character.mjs --file ../member/42/log.cgi --mode multi --username migrated42 --apply --accept-partial
```

Windows PowerShell 可在目前的工作階段中設定：

```powershell
$env:TOWN_IMPORT_PASSWORD = Read-Host '請輸入新的 Web 登入密碼'
```

執行成功會建立新帳號與角色，並在 `web/data/legacy-backups/` 留下原始 CGI 的完整位元組備份；在 Unix 系統上以只有檔案擁有者可讀的權限建立，原始來源檔案不會被修改。**備份本身可能包含原版明文密碼，應將它保留在受保護的管理者環境中，勿公開或提交至 GitHub。** 多人登入密碼僅以新 scrypt 雜湊保存，原版的明文密碼不會寫入新帳號資料表。

已匯入的原版 ID、原名稱、來源檔案基本名稱、來源 SHA-256 摘要、欄位數、尚未移植欄位與警告，記錄在 `legacy_character_imports` 表，**同一原版 ID 不可重複匯入**，角色名稱或帳號與現有資料衝突時也不會覆蓋。備查欄位不包括原版密碼、連線主機或瀏覽器資料。匯入交易若失敗，不會留下部分角色、普通與定期存款。

### 目前的實際對應與限制

已對應原版現金、普通存款、超級定期存款、17 種能力、性別、身高體重、職業名稱、職業經驗、工作次數、已精通職業、部分學校時間與角色首次建立時間。原版職業若找不到對應表，會暫用日薪打工並提出警告，不擅自產生不存在的新職業。能量值超出 Web 版公式上限時會限制在目前上限內，並於預覽警告；原版獨立的能量恢復時間暫時重新開始計算。

**目前仍屬部分轉檔**：角色匯入工具本身尚未包含原版婚姻、住宅與土地、疾病、物品裝備、貸款負債、商店企業、歷史帳簿、郵件與其他角色關聯資料（物品可另依第十九階段的 `mono.cgi` 工具安全封存，部分已支援消耗品可依第二十階段規則手動使用），原始城鎮所在地也尚無可可靠對應的個人存檔欄位。已有貸款的角色仍會顯示未移轉負債的警告，不能把匯入結果當作完整且經濟狀態等價的原版角色。所有原始資料保留在外部備份，留待下一階段逐步實作。

**安全與準確性限制：** 目前自動測試使用依原始 69 欄格式建立的合成資料，尚未拿到真實非空白角色檔作全面驗證。請先使用 `--preview` 檢查欄位與數值；資料匯入前需確認角色所有權並取得管理者授權，切勿公開舊版存檔。

## 住宅貸款與每日還款（第十二階段）

原版 `basic.cgi::loan` 將可借額度定為 `int(職業薪資 × 職業經驗/50 × 任職次數/50 + 普通存款×2 + 超級定期存款×2.5)`，向下取整至一萬元，最高三億元。原版提供 12、24、36、48、60、72、84、96、108、120 期，總利息分別為 5% 至 14%，每期款為本金乘 `(1 + 總利息率)` 再除以期數並向下取整。借款時一次將完整評估額度撥入普通存款，未清償前不得再次借款。Web 版所有試算與金額均由伺服器重新計算，不信任前端提交的額度或每日金額。

在銀行的「住宅貸款與融資」區域可以檢視目前額度與各期方案，選取方案後借款；有未清償貸款時則顯示每日還款、剩餘期數、待清償總額與歷史未繳次數，可從普通存款一次清償。借款、撥款、扣款及提前清償均寫入原來的銀行交易帳簿與新增的 `bank_loans` 表。舊版 Web 資料庫啟動時自動建立新表，不覆蓋原始角色及存款。

已核對原版 `town_maker.cgi::login_view` 的結算順序：跨日進入遊戲時先計算普通與定期利息，再扣當天貸款。Web 版在每天首次讀取角色狀態時執行同一順序，**不會在同一日重複扣款，也不會一次追收多日未登入的期款**。借款當天不立即扣第一期，下一個遊戲日開始扣款；結清或期數用完後不再自動扣款。

**與原版的負餘額差異：** 原版直接從普通存款扣除貸款日額，可能使普通存款變成負數。Web 版為維持現行非負餘額模型，若當日普通存款不足，會記錄一次未繳、保留期數及債務，當日不再重試，下一個遊戲日重新嘗試。未繳不會自動免除剩餘債務，亦不另行加收未經原始碼確認的違約金。這是明確的安全性差異，尚未完全還原原版逾期處理。

**轉帳重試安全性：** 前端送出轉帳後若回應因網路問題遺失，保持相同收款人與金額再次送出時會沿用先前的請求識別碼，避免同一操作被重複扣款；成功後才清除暫存識別碼。重新整理頁面後的跨工作階段重試仍需管理員透過 `bank_transfers` 核對，尚未提供完整的交易查詢頁面。

原版舊角色的 `loan_nitigaku` 與 `loan_kaisuu` 尚未從 CGI 存檔匯入；本功能只建立新的 Web 貸款，不能以原版資料完全等價轉移既有負債。多人公開部署及稅務互動仍需進一步審查。

## 食堂、飽足度、體型及工作狀態（第十三階段）

這一階段以 `town_lib.pl::syouhin_sprit` 的食物欄位解析 `dat_dir/syouhin.cgi` 與 `dat_dir/syokudou2.cgi`，從 `category=食` 的原始資料列取得名稱、標價、熱量及能力增幅。依 `command.pl::syokuzisuru`、`syokuzisuru2`，**食堂結帳金額為食物資料標價的三倍**，每次用餐需間隔至少 **60 分鐘**（`town_ini.cgi::syokuzi_kankaku`）。用餐後依實際餐點增加身體及其他能力，並按 `熱量／1000` 公斤增加體重。餐點與價錢由伺服器原始資料重新讀取，前端不可以自行指定金額或能力值。

食堂展示兩份食品來源，包括中央食堂與第二食堂。**PR #31 已實際移植每日抽選及共用庫存**：兩間各從原版食品資料選出最多 30 道，來源第 25 欄為庫存；菜單與份數存於 SQLite、全玩家共用，隔遊戲日或有貨品項降至 25 道以內時重新進貨。點餐時在同一筆交易中扣金錢、增加原版能力／體重並扣一份庫存，未上架或售完不能下單。原版低庫存補貨把玩家現金可負擔性計入，可能使資金不足的人反覆開菜單觸發補貨；Web **只依實際庫存**判斷，並保留原版售價三倍。原版全局食堂 log 與每城旗標存在交叉關係，仍待舊存檔核實；不能由此推定每城獨立庫存。原始名稱已有中文譯名的部分優先顯示繁體中文，未翻譯餐點保留原名。

飽足度依 `top.pl` 的 `last_syokuzi` 分段：用餐後 1 小時內「飽足」、1 至 3 小時「剛剛好」、3 至 13 小時「稍微餓了」、13 至 25 小時「飢餓」、25 至 49 小時「非常飢餓」、49 至 97 小時「極度飢餓」，之後進入嚴重飢餓階段。不同飽足階段依 `town_maker.cgi` 對角色狀態套用 0.8、1.0、0.9、0.7、0.6、0.5 或 0.3 的係數。原版 `town_ini.cgi` 把未進食導致角色刪除的天數設為 3000 天；Web 版**不自動刪除玩家角色**，僅顯示相對應狀態。

體型依 `town_lib.pl::check_BMI` 用**向下取整的整數 BMI**分類：26 以上肥胖、24 至 25 稍微偏胖、20 至 23 標準、18 至 19 稍微偏瘦、17 以下過度消瘦。角色工作狀態依目前身體與頭腦能量百分比的平均、健康能力值除以 100，再乘飽足與體型係數計算。原版「最佳、良好、普通、不良、差」分別對工作經驗給予 15、10、5、1、負 5 的基數，額外再加入 1 至 5 點亂數；狀態過差時不能工作。Web 版為保持現有非負職業經驗模型，工作經驗下限暫設為零。

**資料升級安全：** 角色表新增 `last_meal_at`（最後一次用餐時間）欄位，已存在的 Web 玩家預設為零，並顯示「尚無用餐紀錄」，在首次實際用餐之前沿用普通工作狀態，不因缺少歷史資料造成永久極度飢餓。新建角色也以相同方式初始化。完成第一次用餐後，飽足與狀態轉為依實際時間計算。這項 Web 相容措施不等於原版首次註冊時的飽足狀態。

疾病指數及醫院診療已於第十四階段加入，工作狀態現在會依病症名稱覆蓋對應經驗基數。原版隨機疾病事件已於第十五階段移植第 4 與 15 號，第十六階段再新增 15 種事件，第十七階段又加入 4 種能量與工作相關事件；尚餘 23 種原版事件、其餘醫療相關物品、原始角色 `byouki_sisuu` 轉入及完整疾病事件循環仍待完成。原版角色存檔中的 `last_syokuzi_split` 亦未匯入；原始素材、CGI 與既有角色的金錢及能力不會被資料遷移重置。

## 疾病指數與醫院（第十四階段）

原版 `town_maker.cgi` 依 `byouki_sisuu` 的以下臨界值分類疾病：低於 0 為輕微感冒，低於 -10 為感冒，低於 -15 為腹瀉，低於 -20 為肺炎，低於 -40 為結核，低於 -70 為腦瘤，低於 -100 為癌症；比對以原始程式的嚴格小於判斷，臨界值本身仍屬前一級。健康時不顯示疾病名稱。輕微感冒、感冒、腹瀉與肺炎會分別把工作經驗基數覆蓋為 **-8、-14、-17、-20**，額外再加入原版 1 至 5 點隨機值；結核、腦瘤與癌症會令工作無法進行。原始 `byouki_sisuu` 預設起始值在目前 fork 仍無法確認，Web 版為既有使用者採用治療後的安全基準 **50**，不推測或補造過去病史。

疾病指數的非疾病狀態變化依 `town_maker.cgi`：最佳狀態 +2、良好 +1、普通 0、不良 +1、差 -3、最差 0。原版「不良」分支實際寫成 `-= -1`，因此是 **增加 1**，本階段保留這個運算結果。原版在畫面流程中計算狀態，可能因多次進入畫面而反覆修改疾病指數；Web 版為防止刷新頁面刷疾病數值，以設定的 `GAME_TIMEZONE` 時區按日期**每個遊戲日最多套用一次**，同一日的狀態查詢不再次增減。第一次遷移進來的角色先建立日期基準，不追溯舊病史或補算數千天數值；沒有用餐紀錄時也不執行飢餓帶來的疾病增減。此部分不等同原版畫面更新頻率。

醫院依 `basic.cgi::byouin` 提供未投保價格：健康時的預防注射 **10,000 元**、輕微感冒 **18,000 元**、感冒 **28,000 元**、腹瀉 **32,000 元**、肺炎 **35,000 元**、結核 **48,000 元**、腦瘤 **64,000 元**、癌症 **88,000 元**。醫院從角色**現金**扣費，成功後疾病指數設為 50，銀行存款及能力維持原狀；錢不夠則整筆交易失敗，不會部分扣款或治療。原版持有「健康保險」可將費用向下取整為三分之一；此部分已在第十八階段加入，Web 現在由伺服器查詢角色本人**尚在有效期內**的保險，不接受瀏覽器自行宣稱已投保。未投保或已到期時收完整醫療費。

特別差異：原版 `basic.cgi` 醫院畫面明確標示腦瘤醫療費 **64,000 元**，但伺服器實際判斷治療費的 `elsif` 分支漏掉了腦瘤。Web 版按畫面價錢收取，避免因未定義的治療費出現非預期的免費治療；這是刻意修正原始碼不一致，而非宣稱原版兩處相同。

資料庫透過 `ALTER TABLE` 非破壞式增加 `characters.health_index` 與 `characters.last_health_day`；舊帳號、金額、職業、能力、飲食、住宅及其他紀錄均不重置。角色快照包含 `health`（疾病名稱、指數、最近結算日期）與 `hospital`（現時醫療費），治療 API 為 `POST /api/hospital/treat`，只操作已驗證的目前玩家角色。新加入 `src/health.mjs`、`tests/health.test.mjs`，涵蓋所有疾病臨界值與價目、每日一次、疾病對工作經驗的影響、無錢拒絕治療、單機／多人玩家隔離。

原版造成風寒的第 4 與 15 號隨機事件已於第十五階段接入，第十六階段新增 15 種無道具事件，第十七階段新增 4 種能量與工作相關事件；其餘 23 種事件、健康保險以外的物品與原始購買存檔、疾病及用餐歷史 CGI 匯入仍待完成；Web 不會自行產生無來源的疾病事件或任意改變其他玩家的健康。

## 原版隨機疾病事件與個人事件紀錄（第十五階段）

已核對原版 `event.pl::event_happen`：每次進入事件流程時會先使用 `int(rand(3))+1`，**只有結果為 1 時**才繼續使用 `int(rand(44))+1` 抽出事件編號。原版 44 種事件中，這一階段只移植直接修改 `byouki_sisuu` 的兩種：**第 4 號「感冒了」**直接將疾病指數設為 **-15**；**第 15 號「裸體睡覺而身體不適」**直接設為 **-8**。這兩種事件都以賦值覆蓋目前疾病指數，不是從目前指數扣除 15 或 8。各事件本身在原版事件流程中的單次機率為 1/132，合計約為 1.515%。

**抽取頻率差異：** 原 CGI 在進入 `login_view` 後會呼叫 `event_happen`，因此多次進入主畫面可能多次抽取。Web 版為避免重整、網路重送或每次 API 回應都刷事件，改為依 `GAME_TIMEZONE` 時區每個遊戲日最多抽選一次。新安裝或舊版 Web 角色第一次載入時只登記當日抽選基準，不倒推並補發過去日子的事件；次日首次讀取角色狀態才開始抽選。即使只抽到未移植的其餘 42 種事件，仍會計入當天已抽選，但**不會虛構未實作事件的能力、資產或物品效果**。

伺服器在完成當日疾病指數的原始狀態調整後再抽取隨機事件，沿用 `town_maker.cgi` 中狀態判斷後呼叫 `event_happen` 的先後次序。事件與 `last_event_day` 以同一筆 SQLite `BEGIN IMMEDIATE` 交易寫入：若成功抽到第 4 或 15 號，角色疾病指數與 `character_events` 事件紀錄一併保存；若出錯則一起回滾，因此同日後續狀態刷新不會再次獲得另一個事件。多人模式的事件紀錄依 `user_id` 隔離。

角色資料庫新增 `last_event_day` 欄位，舊 Web 資料庫自動以空字串升級，不影響現有角色或其他房屋、金錢、訓練與銀行資料；新表 `character_events` 保存日期、原版事件編號、疾病指數變更前後與時間。醫院介面下方顯示最近最多 15 筆本人疾病事件。此階段不移植原版其他 42 種事件、事件新聞、事件音效或其個別道具效果，後續可以延伸同一事件紀錄架構。

## 原版無道具現金、能力與體重隨機事件（第十六階段）

延續第十五階段的 `event.pl::event_happen` 兩層抽選，不改動原版的事件編號、三分之一觸發機率及 1 至 44 的均勻抽取。這次新增 15 個不需要原版物品持有／商店系統的事件分支，連同原本疾病第 4 與 15 號，共計支援 17 種：

- **現金與抽獎：** 第 1 號扒手（先抽 1 至 100,000 元，再二分之一機率損失該金額或抓到扒手獲得等額謝禮）、第 2 號撿錢包（獲得 1 至 10,000 元）、第 5 號 NHK 收費（扣 1,000 元）、第 13 號幸運抽籤（獲得 1 至 15 萬元）、第 24 號樂透（十分之一機率再抽 100 至 1,000 萬元獎金，否則花費 3,000 元）、第 41 號自動販賣機找零（獲得 1,000 元）。
- **五個學科：** 第 7、8、9、10、12 號，分別影響國語、數學、理科、社會、美術。各自二分之一機率增加或減少 3 點。
- **其他能力：** 第 14 號溫柔心情，使 LOVE（愛）增加 5 點。
- **體重：** 第 6 號失戀暴食使體重增加 5 公斤，第 25 號被大阪阿姨說教使體重減少 1 公斤，第 43 號失戀食慾不振使體重減少 5 公斤。體重變更後同步更新 BMI。

**數值差異：** 原版 `event.pl` 有些扣款可直接讓現金變成負數，減少能力或體重也沒有明確的下限。Web 版目前不支援負現金或負能力，因此事件扣除現金和能力時最多扣到 **0**；體重最低為 **0.01 公斤**，以維持有效 BMI 計算。這些下限是 Web 版的資料完整性保護，並非原版的遊戲規則。所有實際扣除量都寫入事件描述及 `effects_json`，避免發生金額不足時帳面顯示與資料庫不一致。若獎金或能力增加超過 JavaScript 安全整數上限，整筆事件交易會回滾，當日仍可重新嘗試抽選。

**原始機率與先後次序：** 每個遊戲日只使用原版的兩層事件亂數選出編號，選到上述 17 種才依該事件自己的二次抽選處理分支；選到其他 27 種尚未支援的事件不產生額外資產、道具或能力變化。此次沒有改為只在已支援的 17 種事件之間抽選，因此每種已支援事件仍佔每日事件流程的 1/132。每日頻率仍沿用第十五階段的 Web 安全規則，與原始 CGI 可於多次進入主畫面抽選不同。

**資料庫遷移：** `character_events` 在保留原始欄位與既有疾病事件歷史的情況下，透過 `ALTER TABLE` 增加動態敘述 `description` 與實際數值變化 `effects_json`；新事件所需的現金、體重、BMI 與能力繼續儲存在現有 `characters` 欄位，不重設既有角色。抽選、扣款、能力變化、事件紀錄與每日抽選日均以單筆 `BEGIN IMMEDIATE` 交易完成，避免當日重送重複獲得獎勵。前端另外建立「最近的隨機事件」面板，僅顯示已登入玩家自己的歷史，最多保留最近 15 筆於畫面。

原版其他 27 個事件牽涉道具、交通、能量、工作經驗、優惠券、玩家新聞或其他互動，目前不當成已移植。原始碼中的第 45 與第 46 號事件因抽選範圍固定為 `rand(44)`，此流程實際不會抽到，Web 版同樣不將它們放入隨機池。

## 能量與工作經驗隨機事件（第十七階段）

本階段查核 `event.pl::event_happen` 的第 **26、27、33、39** 號事件，沿用第一層 1/3、第二層 1 至 44 的原版均勻抽選，不將未支援的其他事件重新分配機率。原版 44 種事件已有 21 種可在 Web 版產生效果。

- **26 號：街頭衝突。** 原版再用 `int(rand(5))+1` 抽取五種結果。第 1 種從現有身體能量扣除 `floor(身體能量/3)`；第 2 種從頭腦能量扣除 `floor(頭腦能量/3)`；第 3 種同時從兩者各扣除 `floor(能量/4)`；第 4、5 種順利逃離，不影響能力或能量。Web 版保留五種分支各 1/5 的機率，事件紀錄會顯示實際扣除的點數。
- **27 號：溫泉招待券。** 原版無條件將身體與頭腦能量各增加 1,000 點。Web 版採原有能量上限模型，兩種能量分別最多回復到當下能力值對應的上限，不允許超過上限。這是與原版直接相加不同的處理，若角色本來已滿能量，實際回復量為 0，並會照實寫在事件紀錄。
- **33 號：地方偶遇。** 再依 `int(rand(3))+1` 抽選三種等機率結果：遇見吉本藝人，有趣度增加 3；在奈良被鹿踩踏，身體能量扣除 `floor(身體能量/3)`；在琵琶湖溺水，身體能量扣除 `floor(身體能量/2)`，並支付 50,000 元救援費。Web 版現金不足時最多扣至 0，不允許負餘額，實際費用仍記入事件歷史。
- **39 號：工作專注度。** 若事件執行時身體與頭腦能量**都至少 500**，工作經驗增加 10；否則減少 5。此處使用原版當下能量的絕對值門檻，並不依角色工作冷卻、職業或是否真的完成一次工作重新判斷。Web 版職業經驗下限為 0，因此低經驗角色的實際扣點可能少於 5。

**能量恢復計時：** 原版能量恢復值與其本身上限存在舊系統差異。Web 版為避免事件扣除能量後立即被此前累積的恢復時間抵銷，只要事件改動身體或頭腦能量，就將該角色的 `recovered_at` 改為事件結算當下時間，之後才重新按每 10 秒 1 點恢復。這是為符合 Web 版既有的時間恢復模型所做的安全性規則，並不是宣稱原始 CGI 也會重置恢復時鐘。

**交易完整性：** 這四個事件直接沿用 `character_events` 歷史表的動態說明與 `effects_json`；能量、工作經驗、現金、能力、事件日期與歷史資料都在單筆 `BEGIN IMMEDIATE` 交易寫入。單日相同事件不會重複觸發，若欄位無法通過資料驗證則全部回滾。這一階段不修改原有角色的體型、銀行餘額或工作次數，也沒有將道具、商店或戰鬥事件假裝為已實作。

**驗證：** 新增單元與 SQLite 整合測試，涵蓋五種街頭衝突結果、溫泉能量上限、三種地方偶遇、工作經驗 500 點雙能量門檻、實際恢復時鐘、事件紀錄、多用戶隔離、資料保護及錯誤回滾。

## 原版健康保險、持有物與醫院折抵（第十八階段）

本階段建立可供後續擴充的 `web/src/inventory.mjs`，從原始 `dat_dir/syouhin.cgi` 精確定位 `日用品<>健康保険`，讀取第 18 欄原始價錢 **10,000 元**、第 22 欄耐久 **30**、第 23 欄單位 **「日」**。原版 `town_ini.cgi` 指定最多 **25** 種持有物、同種物品每次選購至多 **5** 份；現階段**只支援健康保險一種物品**，尚未實作其他 24 種的完整種類上限管理，也不能使用其他原版物品。購買來源會顯示原始商品名稱與繁體中文「健康保險」。

**臨時購買入口與原版差異：** 原版道具通常透過玩家店面、百貨或販賣機依當日商品上架、店家售價與其他條件買入，百貨價錢可能不同於原始商品標價。Web 版尚無完整商店，為讓醫院功能可驗證，提供單獨「健康保險與個人物品」購買區，以**原始商品基準價 10,000 元／份**由角色現金扣款，並明確標示這不是忠實移植完整百貨商店與庫存的購買流程。沒有通用商店購物 API，也不能任意指定道具價格、種類或折扣。

原版健康保險使用「日」耐久、購買時持有量可合併。Web 版以目前尚未到期的剩餘毫秒數加上 `購買份數 × 30 天` 建立單一有效期限；一次接受 1 至 5 份，**所有剩餘耐久加總不得超過 150 天**。此持有物計算是沿用原版耐久語意的 Web 實作，並非完整還原原版 `buy_syouhin` 的逐日取整與堆疊餘數演算法。現有保險過期後可重新購買，重新購買不會回溯延長先前已過期的期間。

在 `GET /api/state` 的 `insurance` 欄位顯示有效與否、剩餘日數、到期時間、價格以及限購條件；`insurancePurchases` 顯示個人近期最多 20 筆保險購買紀錄。`POST /api/inventory/insurance/buy` 使用 `{quantity,requestId}` 購買，並以 `(user_id,request_id)` 唯一限制確保同一請求重送不重複扣款、不得用同一識別碼修改數量。錢不夠、份數超額或有效期超額會在同一 SQLite 交易中整筆拒絕；所有購買以伺服器目前商品價格計算，瀏覽器不可以指定商品資料、金額或其他角色帳號。

醫院 `GET /api/state` 的 `hospital` 費用及 `POST /api/hospital/treat` 現在會查詢 `inventory_items` 中**本人的有效健康保險**，只要有效，醫院各病症費用（包含健康時的預防注射）就按原版公式 `floor(原本費用 / 3)` 折抵，治療不會消耗保險或變更其到期日；有效期滿則自動恢復完整價格。折扣判斷與醫院扣款都在同一筆角色交易中執行，多人模式亦不能自行傳入 `insured`、`discount` 或 `userId` 來冒用其他玩家的保險。需注意原 CGI `basic.cgi::byouin` 對 `mono.cgi` 的保險判定只檢查名稱，其過期物品通常由持有物畫面另行整理；Web 版改為每次診療主動核對有效時間，因此原作在未清理過期紀錄時的行為可能不同。

資料庫新增 `inventory_items`（個人道具有效期限）及 `inventory_purchases`（交易歷史與請求防重）兩表，既有角色、銀行、貸款、房屋、疾病、飽足度與事件紀錄均不重置。已驗證單機及多人購買、30 天到期、續購、五份限額、現金不足回滾、重送不重扣、他人資訊隔離、醫院折抵與到期恢復原價。第十九階段已補上原始 `mono.cgi` 的逐筆封存與部分保險還原；第二十階段已支援部分原始消耗品使用，後續仍需支援剩餘特殊道具、完整物品使用／販售、角色裝備關聯、原作商店供需及保險以外道具的事件效果。

## 原版 `mono.cgi` 物品存檔預覽與安全封存（第十九階段）

原版 `town_lib.pl::syouhin_sprit` 的物品紀錄為 **33 個欄位**，每筆使用 `<>` 分隔，包含種類、原名、各項能力效果、特殊效果、價格、剩餘耐久、耐久單位（「日／回」）、間隔、最後使用時間、備註、購買時間及原始單價。本階段新增 `src/legacy-inventory.mjs` 與 `scripts/legacy-inventory.mjs`，可以不執行 Perl、不更動原始檔案的方式讀取 `member/<原版ID>/mono.cgi`。此 fork 尚沒有可驗證的真實玩家物品存檔，因此測試使用嚴格對應原始欄位的合成資料；尚需持真實資料做回歸確認。

**先使用第十一階段的角色匯入工具，把對應 `member/<ID>/log.cgi` 角色匯入至 Web 資料庫。** 物品匯入必須使用完全相同的 `--id`，並核對 `legacy_character_imports` 既有映射。不能指定任意 Web 玩家接收其他人的原始物品，也不會為不匹配的角色建立新帳號。存檔中的物品備註不會直接執行，也不當作 HTML 載入。

在 `web/` 目錄先預覽（不會修改資料庫、不會寫入備份）：

```sh
node scripts/legacy-inventory.mjs --file ../member/00042/mono.cgi --id 00042 --preview
```

確認原始角色 ID、來源內容與各項物品預覽後，**先關閉 Web 伺服器並備份 `web/data/`**，再選擇單機或多人資料庫正式匯入：

```sh
node scripts/legacy-inventory.mjs --file ../member/00042/mono.cgi --id 00042 --mode solo --apply --accept-partial
node scripts/legacy-inventory.mjs --file ../member/00042/mono.cgi --id 00042 --mode multi --apply --accept-partial
```

命令中的 `00042` 只是示例，必須換成角色匯入時實際使用的原版 ID，前導零也要完全相同。 `mono.cgi` 本身沒有角色 ID 欄位，工具會拒絕標準 `member/數字ID/mono.cgi` 路徑與 `--id` 不一致的情況；從其他備份路徑匯入時仍需由操作人員核對來源身分。`--accept-partial` 表示同意只還原目前已確認的物品規則：健康保險及第二十階段所支援的消耗品；其他道具仍僅封存。來源檔案限 4 MiB、最多 2000 筆物品，欄位結構不合格時直接拒絕匯入，不擅自猜測欄位、略過錯誤行或自動修復。原始 bytes 以 SHA-256 摘要與存取權限受限制的原始備份分開保存到 `web/data/legacy-backups/`；支援 UTF-8 與 Shift_JIS 的讀取，不會把敏感備份推送到 GitHub。正式匯入在 SQLite 交易中寫入封存物品與匯入稽核，失敗時不留部分新資料或覆蓋角色。

在 Web 版「健康保險與個人物品」區塊新增「原版物品存檔」唯讀清單，供本人查看原始種類、名稱、耐久及來源行號，最多列出前 50 筆；已確認的「回」耐久消耗品自第二十階段起可手動使用，但**未實作的特殊效果、交易、出售、裝備與傳送功能仍不會開放**。資料庫 `legacy_inventory_items.raw_fields_json` 保存每筆原始 33 欄，`legacy_inventory_imports` 保存原版 ID、對應玩家、來源摘要、檔名、筆數與匯入時間；同一個原版 ID 或目標玩家只允許一次，避免重複領取同批物品。這兩張表屬額外新增，不覆蓋第十八階段的 Web 原生保險交易紀錄。

**健康保險的部分還原：** 只有原版「日用品／健康保険」且購入時間和日耐久均有效時，才將 `購入時間（Unix 秒） + 原始耐久天數 × 24 小時` 換算成 Web 的保險到期時間，讓本人在剩餘有效期內直接享有醫院三分之一的折扣。若已過期，僅封存歷史不啟用；若 Web 角色已存在保險紀錄，**拒絕用仍有效的原始保險覆蓋 Web 現況**，不會將可能重複的兩份保障任意相加。原版若出現多筆健康保險，因無法確認正確的耐久堆疊方式，工具會拒絕自動合併而要求先整理來源。Web 版折扣判斷以實際到期時間為準，可能與原版 `basic.cgi` 在未清理過期持有物時只依名稱判定的做法不同。

第十九階段完成的是**原始物品資料的安全保存與部分功能還原**，第二十階段在不改寫原始封存的前提下加入部分消耗品的實際使用；仍不是原版完整道具系統。其他道具仍需依原版效果、使用間隔與耐久、原版店家來源、交易價格及物品持有上限逐項實作。第十九階段新增測試涵蓋原版欄位位置、亂碼與格式錯誤、來源 SHA-256、身分對照、保險到期、既有 Web 保險衝突、保護性備份、重複匯入及多人唯讀資料隔離。

## 原版消耗品使用與耐久紀錄（第二十階段）

本階段根據 `basic.cgi::item_do` 的原始執行順序，在原始 `mono.cgi` 安全封存的基礎上加入**可確認效果的「回」耐久消耗品**使用。必須先完成角色匯入及第十九階段 `mono.cgi` 物品匯入；本階段沒有通用道具商店與道具購買 API，也不會替新角色憑空產生物品。符合條件的舊物品會在「原版物品存檔與消耗品」中出現「使用一次」操作按鈕。

**本次支援：** 道具原始 17 項能力增減；疾病類型為「風邪、下痢、肺炎、結核」且角色正好罹患對應疾病時的疾病指數增加；另支援「万能／萬能」藥物不限制疾病類別，直接依藥效增加疾病指數；「ウエイトアップ／增重」、「ダイエット／減重」、「身長／身高增加」及「縮み／身高縮減」效果；使用後的身體與頭腦能量成本、熱量造成的體重變化；耐久單位為「回」時每次使用扣除 1 次。原版 `basic.cgi` 對非對應疾病的藥品仍允許使用，只是不增加疾病指數，因此 Web 版同樣會消耗其一次耐久。每項增減與實際消耗皆由伺服器讀取封存的原始欄位，不接受瀏覽器直接指定能力值、藥效、物品名稱、金額或其他玩家身分。

**原版錯誤修正：** 原始 `basic.cgi::item_do` 的萬能藥判斷條件寫成 `if ($koukahadou eq "万能\")`，雙引號被反斜線跳脫，與原本「依效果名稱判定」的寫法不符。對照同一函式緊接著的風邪、下痢等藥效分支，以及 `dat_dir/syouhin.cgi` 中多種 `万能,數值` 藥物的「治療所有疾病」描述，可以明確還原作者意圖：當特殊效果為 `万能` 時，**不論目前是什麼疾病或健康狀態，直接增加該道具記錄的疾病指數**。Web 版已加入此修正並測試，原始 CGI 留作參考不予覆蓋。這項修正不表示原版實際執行時一定能正常處理該行，也不會代替其他未完成系統。

**未開放：** 其他未定義或多段效果、`ランダム品` 隨機物品、禮物及原版裝備類別，以及耐久單位「日」的非保險道具，仍不在可使用清單內。這不表示它們在原版中不可使用，只是 Web 尚未移植其完整效果。原始健康保險繼續由第十八及第十九階段的到期制度提供醫院折扣，不從「回」耐久消耗品介面使用。

**使用間隔與用餐：** 使用前檢查原始 `syo_siyou_date + syo_kankaku × 60 秒`，同一物品冷卻時間未結束時拒絕；身體或頭腦能量不夠支付原版消耗時亦拒絕。`食料品` 與 `ファーストフード` 類別同時遵循第十三階段食堂的 **60 分鐘用餐間隔**，成功使用才重設最後用餐時間；道具熱量會依原始 `calories / 1000` 公斤反映到角色體重。一般非食品物品不重設用餐時間。

**保留 Web 版既有數值安全限制：** 原版直接累加能力及身高體重、扣除使用能量，並可能使部分數值降至零以下；目前 Web 版能力不能為負、身高最小 1 公分、體重最小 0.01 公斤，能量不能高於按現有能力推得的 Web 上限，也不能為負。負數能量成本依原始欄位視為能量恢復，但最多恢復到 Web 上限。道具使用後以當下時間重新開始 Web 能量恢復計時，這些上限及計時處理是既有 Web 模型的明確差異。對角色原始 33 欄的所有可能異常值會保守驗證，不會將未確認的特殊效果當成普通能力加成。

**資料與重送保護：** `legacy_inventory_items` 仍保存第十九階段匯入的原始 33 欄，**不會因使用物品而修改**。新表 `legacy_item_usage` 另存目前剩餘次數與上次使用時間（毫秒），`legacy_item_use_history` 留存實際能力、疾病、體型與能量變化。使用 API `POST /api/inventory/legacy/use` 接收 `{sourceLine,requestId}`；以 `(user_id,request_id)` 避免網路重送重複消耗，禁止用同一識別碼改用其他物品。能力及疾病修改、扣除耐久與歷史紀錄均包在同一筆 SQLite `BEGIN IMMEDIATE` 交易中，任何步驟失敗都會回滾。前端重送相同物品時會盡量沿用尚未成功確認的識別碼，但瀏覽器重新整理後不保證保留未完成請求。

**多人隔離與顯示：** 伺服器只查詢登入者自己的舊道具封存及使用紀錄。只有已解析且支援的道具顯示操作按鈕；原始內容異常的封存項目不會使整個角色狀態 API 故障，而是保持唯讀、不顯示可用動作。個人清單仍最多列示前 50 筆，使用紀錄顯示最近 20 筆；原版其他商品、裝備與店家買賣仍待分階段完成。

角色表以非破壞式新增 `kpoint`，舊 Web 玩家預設為零；原始 Perl 69 欄角色中的 `kpoint` 目前僅保留於封存，**不會自動補進新欄位**，因此畫面顯示的是 Web 版 K 點數。原 CGI 可以讓外貌降到負值，Web 沿用既有能力非負限制，最低為 0；當原角色外貌不足 3 點時，歷史記錄實際減少量。原 Perl 事件前段亦能處理其他觸發來源，本階段只提供已移植的 #44，不把尚未完成的第 34 號聖誕事件當作已支援。若玩家逾期未按按鈕，挑戰不會發獎；點擊後確認為逃走並寫入事件歷史。

新增單元及 HTTP 整合測試，涵蓋 20 秒邊界、賞金範圍、K 點數、外貌保護、多人隔離、重送防重、金額上溢、紀錄失敗完整回滾、每日限一次與來源對照。總進度 **37/44**，待完成 #28、#34～#38、#40，共 **7 種**。

## 四次元福袋事件（第二十八階段）

原版 `event.pl::event_happen` 的 **第 35 號**並非一般道具購買；`dat_dir/prezento.cgi` 確實有 `プレゼント<>４次元福袋`、耐久 **10 回**的原始商品資料。此階段不新增百貨購買或新道具取得方法，只讓**經既有 33 欄原版物品封存匯入、尚有「回」耐久、非「ギフト」分類**的玩家物品觸發事件加成。

原版會**先抽 1～4 種結果，再檢查福袋**。若無有效福袋，固定罰款 10,000 元（Web 依既有安全模型最多扣至零）；有福袋則先消耗一次耐久並處理以下四種等機率分支：

| 結果 | 對照原始 Perl 的效果 | Web 安全限制 |
|---|---|---|
| 第 1 種 | 現金 **+100,000,000 元** | 溢位時交易回滾 |
| 第 2 種 | 身體與頭腦能量各 **+10,000** | 不超過現行角色的能量上限，記錄實際恢復量 |
| 第 3 種 | 隨機獲得 **1～15 張優惠券** | 沿用 Web 優惠券餘額，與第 30 號事件（1～5 張）共用安全累加及歷史紀錄 |
| 第 4 種 | **原版沒有任何獎勵或敘述分支** | 不虛構收益，仍扣福袋耐久一次 |

抽選仍是**每日最多一次**及原版第 1 層 **1/3 發生機率**、第 2 層 **1/44 事件編號**；不提高第 35 號權重。事件效果、原始物品剩餘耐久、優惠券、每日抽選標記和事件歷史在同一筆 SQLite 交易，失敗會全部回滾，多人角色不共用物品或券數。原始 33 欄存檔保持唯讀。

**注意差異：** 原版 `coupon_get` 操作 `mono.cgi` 的原始優惠券物品，Web 仍只累積自己的 `character_coupons` 餘額；沒有聲稱已完成兌換商店或既有原版券數同步。原始 Perl 能讓能量超過上限、現金負數，Web 遵循現有數值安全邊界。測試覆蓋四種結果、15 種券數、無福袋或無效封存、禮物／日耐久排除、跨日、多人隔離、第四種扣耐久、歷史失敗回滾及上溢防護。

**最新進度：38／44 種事件，尚有 #28、#34、#36、#37、#38、#40 六種未移植。**

## 聖誕老人／蟑螂事件（第二十九階段）

本階段依原版 `event.pl::event_happen` **第 34 號**，及 `dat_dir/prezento.cgi` 的「等身大サンタさん人形」（原始禮物清單列為「プレゼント」、10 回耐久）加入事件分支。只接受**已匯入且可核對的原版 33 欄封存**，不得藉本事件自行購買或產生尚不存在的物品。來源分類為「ギフト」、耐久不是有效「回」或已用盡時，不適用人偶加成。

原作先抽兩種等機率結果，再檢查持有的人偶：

- **有符合的人偶：** 消耗 1 次耐久，第一種將**目前現金翻倍**，第二種讓**身體及頭腦能量各恢復 10,000**。Web 依現有安全模型限制能量上限及安全整數，記錄實際增加數。
- **沒有人偶且現金為 0：** 觸發**德政令**；原版對負現金也有效，但 Web 不保存負現金，因此此分支不會憑空產生新的資金。
- **沒有人偶且現金大於 0：** 在原始第 34 號分支中建立**20 秒蟑螂挑戰**。事件本身不預先發放獎金，玩家必須於 20 秒內拍打；逾時沒有獎勵。

過去 `event-cockroach.mjs` 只准第 **44** 號事件領獎；這次擴充為第 **34、44** 號共用的伺服器驗證挑戰。兩種觸發來源皆依原版使用 **1～20,000 元**獎金、K 點數 **+3** 與外貌 **-3**，同時保持只以伺服器計時、每玩家獨立、不能重領、跨角色禁止、更新失敗完全回滾。事件紀錄保留真正的原始編號 34 或 44。

**測試與回歸：** 新增 `tests/event-santa.test.mjs`，驗證原始 Perl 分支、贈品資料、現金翻倍、兩種能量恢復、零現金德政令、道具耐久與跨日、無效封存、多玩家隔離、#34 與 #44 的倒數與領獎、逾時、防重領、資料庫回滾及溢位防護。不修改原始 CGI 與伺服器 API。

**事件移植進度：39／44 種；未移植 #28、#36、#37、#38、#40 五種。**

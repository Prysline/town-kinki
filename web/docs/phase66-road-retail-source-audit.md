# 第66階段：原版百貨18種載具來源校正、專門店備註與禮品類別核實

日期：2026-11-22。開發基底：第65階段已合併 Web HEAD `5eb194c01e2143f701d58620a1c5fa64178a833a`，工作分支 `feature/web-phase66-retail-all-road-vehicles`。本階段是**修正第65階段來源解讀過窄造成的漏接**，不是發明新商店或解除不明購買條件。

## 一、重新查核實際原版來源（不要憑備註猜行為）

1. `town_ini.cgi` 的 `%idou_syudan` 有20種公路名稱／秒數；原始說明明確指出「乗り物はsyouhin.cgiにある商品でないと意味がありません。ただし商品種別が『乗り物』である必要はありません」。亦即**商品分類不需要是乗り物**，`town_lib.pl::header` 在公路分支用本人持有物名稱辨識，而不是用類別阻擋。
2. `dat_dir/syouhin.cgi` 精確有18筆與原版交通名單對應的百貨商品：**11筆『乗り物』，7筆『ギフト』**；18筆的原始33欄效果皆是 `無`、耐久單位 `回`、備註包含 `※移動手段です。`。
3. `command.pl::depart_gamen` L1410～1515 的兩間百貨從 `dat_dir/syouhin.cgi` 建貨架，排除分類 `食` 及 `秘伝商品` 備註，**沒有**排除 `専門店限定商品` 備註。原版 `command.pl` L769、819 把此備註用來限制 `スーパー` 類型的**問屋進貨**，不可移植為「百貨禁止購買」。目前 Web `retail.mjs` 也已用本人真實交易對應兩間百貨，保留原價×3及每日上架抽選。
4. `hanbai1.cgi` 的 `$hanbai_hinmoku='餌'` 對應餌料類商品，不是載具專賣店。倉庫未找到可用以證明獨立載具專賣店售價及入口的 CGI，不新增虛構車店。
5. 原版 `gifutoya.cgi::gifutoya_do` 與 `command.pl::gift_souhu_syori` 有轉禮／寄禮路徑，但現行 Web `gift-shop.mjs` 的 `__web_gift__` 物品來源和本人購物收據不是同一種永久對照：寄件者刪帳後原 `gift_events` 亦可能消失。**本階段只開啟原版百貨真購直接入庫的七筆ギフト類別車**；轉換、送禮及受禮者再開車，待建立可跨刪帳保存的來源證據，不因相同名稱冒認合法交易。

## 三、本階段的程式與安全合約

- `road-travel.mjs` 的 `parseOriginalRoadTransport` 由5種擴大為上述18筆，啟動時逐項核對原始行號、SKU、分類（11乘り物／7ギフト）、效果、耐久單位、備註及20種原版交通速度。來源不符合直接拒絕，不以用戶名稱或任意傳入的 JSON 代替。
- `availableVehicles` 使用本人 `legacy_inventory_items`、原始33欄與 `legacy_item_usage`，並額外確認 `retail_purchases` 的本人／行號／SKU／商品名／真正 `depart1` 或 `depart2` 收據。原版這兩種分類都可能在真正的百貨貨架售出，但只有真實已買入且尚有剩餘耐久的物品會入交通選單。
- 公路 `POST /api/road/start`、抵達、電車互斥、1/10事故、迷路與輪滑車效果、單車鍛鍊、車資、SQLite持久行程與請求冪等全部不變；第65階段已持有且有有效收據的車仍自動適用。無新API、無新資料表或非破壞遷移。
- `public/app.js` 清楚區分「百貨禮品」與一般「百貨」／「寶箱」載具，UI 使用安全文字DOM，避免把『禮品』錯誤顯示成不能移動。
- 禮品屋交易本身不改動；本階段不宣稱已支持受贈載具開車，也不修改原始 CGI 2010年活動有效期。

## 四、計劃偏差稽核與改正

| 稽核項目 | 判定 | 修正及保留界線 |

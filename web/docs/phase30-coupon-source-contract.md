# IT-04：原版優惠券獎品資料來源與交易前置

> **歷史基準（第30階段，2026-11-20）**：依原始 [`coupon.cgi::coupon_do`](../../coupon.cgi#L120) 和 [`dat_dir/coupon.cgi`](../../dat_dir/coupon.cgi) 檢查，當時只做唯讀解析。**2026-11-21 第51階段**已完成 [只使用 Web 事件所得券的實際扣點／原始33欄獎品入庫／交易帳本](phase51-event-coupon-redemption.md)；原版匯入券仍唯讀，沒有與 Web 事件券相互轉換。

## 已確認的原版行為

原版 `coupon.cgi::coupon` 由 `member/<ID>/mono.cgi` 找種類 `ギフト` 且名稱 `クーポン` 的紀錄，顯示其 `syo_taikyuu` 耐久作為持有**券點數**。兌換 `coupon_do` 再根據表單所選獎品行序讀 `dat_dir/coupon.cgi`，以商品原名雙重核對，依類別 `クーポン交換品:N` 的 N 點扣券，添加完整原始獎品資料至個人持有物。共 30 筆獎品，每筆以原始商品 33 欄資料儲存；獎品的 `回`／`日` 耐久是**獎品本身**的屬性，**不是優惠券的跨日到期時間**。

[`web/src/coupon-catalog.mjs`](../src/coupon-catalog.mjs) 在啟動交易流程前先建立可測的只讀解析：保留原序號、原名、扣點數、獎品耐久單位與原始 33 欄，檢查缺欄／越界／不合法值，並提供序號加原名比對。範圍內測試在 [`coupon-catalog.test.mjs`](../tests/coupon-catalog.test.mjs)。

## 第30階段提出的下一個交易門檻（歷史紀錄）

- Web `events.mjs` 的 `character_coupons` 保存**Web 事件獲得的券**；原版匯入物品則在 `legacy_inventory_items` 的唯讀封存中。兩者目前沒有等價的統一可扣款帳本。必須先設計來源區分、初次匯入、扣點數策略、拒絕雙重計數；不得私自把所有原始「クーポン」或複數持有物加總為 Web 可花券。
- 原版獎品須以完整 33 欄新增為**可追蹤的本人持有物實體**，不能只增加 `character_coupons` 的值或造一個顯示字串。須先統一背包上限、同品堆疊、扣耐久及原版可用道具效果的讀取路徑。
- 扣券、交付獎品、交易歷史、request ID 防重與多人隔離必須在同一 SQLite 原子交易中；金額／原始序號／獎品原名以伺服器已解析來源為準。
- 必驗券點數不足、無券／舊券來源未核准、商品序號與名稱不符、背包額滿、重複提交、同時兌換、插入失敗回滾、匯入舊檔不被覆寫。原版直接重寫 mono.cgi 有資料競態風險，Web 不照搬不安全檔案覆寫。
- 完成實體獎品交易前，**不新增可點擊「兌換」按鈕，也不在 Web 畫面稱已可兌換**。不得以獎品的 `日` 耐久推定優惠券持有點數會跨日消失。

**第51階段狀態**：Web 事件券的真實兌換、本人25格背包上限、原始33欄獎品、帳本／防重及 rollback 已有實作與測試；但**舊版匯入券的正確轉換、部分獎品的實際用途與原版整套持有物規則仍未完成**。因此 IT-04 仍是**部分完成（Web 事件券兌換子流程已實作）**，不能宣稱完整原版相容。

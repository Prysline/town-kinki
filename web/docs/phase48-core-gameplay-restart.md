# 第 48 階段：工作門檻與主要遊戲循環重啟驗收

> **現行範圍**：只重製原版玩法，不需要舊玩家存檔匯入、相容與真實舊玩家檔驗收；以 [專案範圍決策](project-scope-no-legacy-player-import.md) 為準。

日期：2026-11-21。PR 只以 `feature/web-dual-mode-phase1` 為整合目標；`master` 保留原版。

## 原版 CGI 可核對的規則差異（WK-06）

- 原版 `basic.cgi::job_change` 選職時會逐項核對 17 項能力、BMI、`$job_sex` 性別、`$job_sintyou` 身高、已精通前置職業。
- 原版 `basic.cgi::do_work`（約 2838～2940 行）在**正式出勤時**重新核對 17 項能力、BMI、身體／頭腦能量及工作間隔；同段沒有再次檢查 `$job_sex`／`$job_sintyou`。
- 第47階段以前的 Web `web/src/engine.mjs::performWork` 誤呼叫共用 `eligibility(current,job,false)`，只略過前置職業，卻保留轉職專屬的性別／身高限制。角色入職後身高改變、且仍有足夠能力、BMI 和能量時，可能被額外封鎖出勤。
- 本階段把「應徵時才檢查」與「已任職每次出勤仍須檢查」明確拆開；**轉職門檻不放寬**，工作仍要求真正持有對應職業、5 分鐘冷卻、原始能力、BMI、能量與身體狀態。性別欄位通常不可由 Web 自行修改，相關分流仍在引擎測試用原始狀態驗證，不加入修改性別的 Web API。
- 這是核對原版後的**玩法等價修正**，不是取消健康與安全限制。原版稅務與未支援物品效果仍不虛構；舊玩家轉檔已排除，僅保護新 Web 存檔。

## 主要遊戲流程端到端驗收

先前各項工作、銀行、購物、物品使用已有單項 HTTP／SQLite 測試，但未有同一個玩家使用**同一份遊戲資料夾跨兩次實際 Node 伺服器重啟**後驗證交易、防重與冷卻的全流程。這一階段新增：

1. 單機以正式 API 建立角色，改為銀行領薪並出勤、存錢，設定實際百貨建築，購買原始商品表可用的「無駄知識を覚える本」並真正使用。
2. 停掉 Node 伺服器**保留 SQLite 目錄**，再啟動全新 Node 程序；核對角色能力、現金／銀行、薪資偏好、工作進度與冷卻、銀行帳簿、原版物品剩餘耐久、購物紀錄、地圖，以及**購物與使用請求 ID 重送不重複扣款／生效**。
3. 再快轉五分鐘工作領取下一筆薪資、正常進食，**第二次真正重啟**核對工作筆數、帳簿、用餐冷卻；跨一遊戲日後核對普通存款只結息一次且無重讀重複入帳。
4. 多人以兩個帳號各自建角、出勤、不同薪資偏好與存款，在**全新 Node 程序**載入相同多人 SQLite，驗證兩人的角色、帳簿、會話 Cookie、工作冷卻及操作權限各自保留；登出舊 Cookie 失效，重新登入仍讀到同一名玩家的帳戶。
5. 另以實際原版「警官」身高門檻設置 HTTP 職業應徵成功，再模擬已任職角色身高下降但 BMI 不變；重選職業仍拒絕、已任職出勤可成功、工作冷卻仍生效。

## 保留的驗收邊界與下一步

- 本階段以 GitHub Actions 實際執行完整 `npm test` 和 Node 語法檢查為自動驗收；**不等於**已用新版 Web SQLite 存檔升級／備份還原或 Chrome／手機實際操作驗收，也不等於原版完整世界系統已移植。
- 多人 HTTP 測試的帳號與地圖是獨立測試資料，不把自動建立的測試城鎮當成原始真實歷史街區。
- 單機快轉只用原有白名單；沒有額外開放任意改時間 API。
- 後續仍優先排查核心循環的阻塞與跨玩家共用資產，再補原版首頁獨立站內信及優惠券帳本，最後選擇具來源的較大型玩法；不因個別商品特效中斷主線。

# 第 47 階段：核心系統優先與跨玩家信件所有權修復

日期：2026-11-21。開發基底：`feature/web-dual-mode-phase1` 第 46 階段，原始 CGI 及既有單機／多人程式為唯一可驗證規則來源。此文件是**優先次序與安全驗收政策**，不是全部功能已完成的宣告。

## 一、方向：從逐項商品特例改為可遊玩的主要流程

已完成的商業、道具、食物與寄禮切片保留，不回滾、不另開第二套虛構商城。此後新 PR 優先回答：玩家能否順利從 **建角 → 工作獲利 → 購買及持有 → 實際使用／交易 → 社交互動 → 重登存檔繼續**；多人玩家是否能確保**自身資產、訊息及交易**不會因另一玩家離開、刪帳、重送或失敗而損失。

原始盤點：[43 個第一層互動入口](phase30-entrypoint-coverage.md)、[14 領域差異與 44 事件盤點](migration-audit.md)、[有來源的待辦](phase30-open-audit-backlog.md)、[原版所有根目錄 CGI 第二層分類](phase30-root-source-classification.md)。這些是追溯地圖；不能把「有入口」當作「已可玩」。

## 三、本階段已修復的實際問題：刪帳連鎖刪除他人信件

第 46 階段在 `gift_mail_messages` 設定 `event_id REFERENCES gift_events(id) ON DELETE CASCADE`，但 `gift_events.user_id REFERENCES users(id) ON DELETE CASCADE`。**只要寄件人刪除帳號，自己的交易事件隨之刪除，收件者名下的信件也會被刪除。**這是 Web 表間關係造成的問題，不是原版 `command.pl::mail_do` 所要求的行為；原版收件與寄件各自寫入角色的 `member/<ID>/mail.cgi`。

第 47 階段在 `web/src/gift-shop.mjs`：

1. 新建信箱表移除對 `gift_events` 的跨帳號級聯外鍵，只保留信件持有者的 `user_id REFERENCES users(id) ON DELETE CASCADE`；`event_id` 保留數字作收發同交易識別，不再是信件存續的前提。
2. 既有第 46 階段 SQLite 信箱表若仍含 `gift_events` 外鍵，於起動時以單筆 `BEGIN IMMEDIATE` 建新表、完整複製原有 id／本人／方向／對方名稱／訊息／禮物／份數／時間、換表並重建索引；遷移失敗整筆回滾。再次啟動不重複遷移。
3. 寄禮時仍維持原本原子交易：扣物品、交收件人物品、`gift_events`、收件與寄件信必須全成功才提交。信件本人的讀取權限不變。
4. 透過 `web/tests/gift-shop.test.mjs` 檢查寄件者刪帳後收件仍在、收件者刪帳後寄件備份仍在、舊 schema 無損轉換及外鍵完整性；`web/tests/server.test.mjs` 檢查真實多人 HTTP 交付後刪寄件者再由收件方重新讀取信件和商品。

本階段沒有假稱已完成「純文字獨立站內信」或歷史寄信匯入，也沒有修改原版 33 欄資料或 `master`。真正的瀏覽器實機與真實玩家備份仍是獨立驗收條件。

## 四、每個接下來的功能 PR 的必備條件

- **來源與玩法**：提供原版具體 CGI／欄位／規則，標出尚無依據處，走完整「取得／使用／結果／重登持續」流程；只測商品標籤不能算可玩。
- **多人與資料**：至少兩個真實玩家角色；驗證所有權、重送、刪除或失敗回滾、資產守恆與存檔重啟。
- **畫面驗證分級**：HTML 結構檢查只叫「結構測試」，不能寫成已完成手機／桌面操作驗收。
- **版本紀律**：獨立 `feature/web-phaseN-...`、PR 目標永遠 `feature/web-dual-mode-phase1`，最新 PR head `push` 與 `pull_request` 兩組 CI 都通過才合併；合併後再次兩組 CI 成功、`master` 不變。

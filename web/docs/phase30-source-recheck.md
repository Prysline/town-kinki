## 三、仍需逐模式盤點的原版子入口

43 個 `unit.pl` 表單入口只是第一層：除了先前已列的 `donut.cgi` 四玩法、`loto.cgi`、`loto6.cgi`、`fukubiki.cgi`、`saikoro.cgi`、`cardw2.cgi`、`otakara.cgi`，[`gamerand.cgi` L206–222](../../gamerand.cgi#L206) 還可再次進入 `obatyan.cgi` 弱／強兩路。入口數量不能當成可玩 CGI 數量。

實際進一步查閱前，不將 `prezent2.cgi` 已成功兌獎、全部競馬／合成配方與獎項、外部 `bbs.cgi`、特殊管理員分流、原版全部行銷活動，直接標成 Web 開發規格。下一層逐模式清冊須包含**來源檔、函式、呼叫入口、資料檔是否存在、權限、扣款／獎勵、Web 路徑、可達性與驗收證據**。

## 四、按既定工作流程繼續

1. **先修文件與來源回歸測試（本 PR）**：校正 `BK-04` 真實稅務來源、`IT-04` 不存在的「到期驗收」、`SC-03` 空資料檔，補齊確定缺口與仍待盤點的區別；不直接修改遊戲數值。
2. **下一個 P1 功能切片**：按 [待辦總清冊](phase30-open-audit-backlog.md) 從原版道具欄位、玩家持有檔、購買與交付的原子交易起步，然後才做優惠券兌換與剩餘五事件；不可把「解析檔案」當成「可使用」。
3. **其餘確定來源逐獨立 PR**：原版定期徵稅需恢復 `k_sousisan/kpoint` 語義及跨日順序；競馬／合成／おばちゃん／口令獎勵各自完成真實規則盤點，確認依賴後再開發，不提前建立假獎勵或安全性不足的交易。
4. 每個功能 PR 必須有來源定位、邊界條件、拒絕／重送／競態測試、CI 成功後才考慮合入整合分支；保留原版 `master`。真正玩家資料及瀏覽器實測前不聲稱完全等價。

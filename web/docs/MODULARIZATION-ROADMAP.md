## 1. 目標與基準

主要單機玩法已具備可持續遊玩及大量回歸證據，適合開始「持續移植＋漸進式模組化」雙軌規劃；不必等待所有單機或真人驗收完成。目標是降低耦合、減少平行開發衝突、提高新增系統及測試的可維護性，而非重做遊戲、平衡數值或提前建立 MOD 平台。

- 原版 master 保持唯讀；正式 Web 基線為 `feature/web-dual-mode-phase1`，長期 PR #1 不合併 master。
- 本次架構查閱快照：`c18f56e8df68f3c8998c1ba7733500026e34424b`。當時 push [46028885558](https://github.com/Prysline/town-kinki/actions/runs/46028885558) 與 PR [46028895284](https://github.com/Prysline/town-kinki/actions/runs/46028895284) 尚排隊；先前 J-5 972/972 是歷史基準，不代表此 HEAD 已通過。
- [現行功能狀態與開發計畫](PROJECT-STATUS-AND-PLAN.md) 仍是移植狀態及排序的權威；本文件不覆蓋現有功能決策與核准範圍。開工前須重查最新 HEAD、tree、CI、開放 PR、現行文件和未提交／未推送工作。
- 原版來源一致性、單元／差分、介面契約及必要整合為完成門檻；真人、自然低機率與長程驗收獨立記錄，不阻擋無關工作。已確認功能缺陷仍阻擋受影響交付。

## 2. 現況與目標架構

現有 src/ 已有 banking、housing、health、training、inventory、retail、fishing、crafting、arcade、road-travel、battle、events 等功能檔案，並非從零模組化。主要集中點（上述 SHA，約略大小／行數）：

| 檔案 | 規模 | 觀察 |
|---|---:|---|
| public/app.js | 257 KB／5,218 行 | 全域狀態、渲染、操作、API、倒數、提示 |
| public/index.html | 89 KB | 集中式畫面結構 |
| public/style.css | 51 KB | 集中式樣式 |
| src/server.mjs | 72 KB／1,403 行 | 初始化、登入、角色、路由、交易、狀態與結算 |
| tests/server.test.mjs | 444 KB／8,001 行 | 大量 HTTP 及跨系統整合 |

採模組化單體（Modular Monolith）：保留單一 Node.js 伺服器、現有 ES Modules、各模式獨立 SQLite，依遊戲功能建立清楚模組介面；不採微服務、不增加框架或另建資料庫。單機與多人共用規則，資料與身分隔離不變。

建議目錄（僅方向，M0 審查後確定）：

- public/app.js：統一啟動入口；core/：api、state、navigation、feedback、clock；modules/：角色、工作、銀行、背包、住宅、商店、釣魚、遊樂、戰鬥、交通、事件；styles/、i18n/ 後續逐步整理。
- src/server.mjs：統一入口；routes/：按領域拆分 HTTP 路由；services/：角色、時鐘、交易、狀態組裝；既有規則檔案先保留，不為移動檔案重寫核心。
- tests/：共用隔離伺服器、帳號、資料庫、時鐘工具；按領域整理 HTTP 測試，保留跨系統整合與所有歷史證據。確認 npm test 仍會發現全部測試。

## 3. 階段計畫

| 階段 | 內容 | 風險／交付 |
|---|---|---|
| M0 | 依賴、入口、資料所有權與副作用盤點 | 低；依賴圖、共用檔責任、現況契約、測試基線、試點範圍 |
| M1 | 前端共用工具及獨立設施畫面 | 低～中；先選骰子等相對低耦合功能，保留 DOM、操作、樣式、倒數及回應 |
| M2 | 按遊戲系統拆 HTTP 路由 | 低～中；保留 URL、方法、請求／回應、錯誤、權限及呼叫順序 |
| M3 | 整合測試及共用測試工具整理 | 低～中；測試清冊、數量及實際覆蓋不倒退，保留跨玩法測試 |
| M4 | 狀態組裝、角色及共用服務分離 | 中～高；先確認結算、RNG、交易與保存契約才拆 |
| M5 | 正式功能模組邊界及公開介面 | 中～高；建立依賴方向、資料所有權與跨領域呼叫規則 |

先完成 M0，再以小範圍前後端試點驗證拆分方式，逐個模組小 PR 整合。不要求所有 M1 完成才開始 M2；但試點及後續的實際順序須依 M0 依賴與現行施工責任決定。M4～M6 不提前全面重構。

## 4. 高風險共用核心

- `mutateCharacter()` 現有 BEGIN IMMEDIATE、角色載入、能量恢復、回呼、角色保存、afterSave、COMMIT／ROLLBACK 的順序與邊界不得改變；不得造成巢狀交易、平行資產權威或部分提交。
- `snapshot()` 不只是讀取：包含銀行利息、能量恢復、每日健康、事件等結算及溫泉特殊唯讀分支。不能直接讓各模組獨立重複結算；保持副作用、時鐘、RNG 消耗順序及狀態欄位。
- 角色、現金、存款、K 點、背包、時鐘、權限、原子交易保留單一權威及清楚契約。
- 初期不改 SQLite schema、歷史 Web 存檔、初始化及升級行為、不新增全域冷卻、不改單機／多人隔離。
- 不重開原版私人 CGI 存檔匯入；不修改既有核准的 Web 安全適配、翻譯識別鍵或來源差異。

## 5. 工作線及版本管理

| 工作線（建議，非已建立） | 責任 |
|---|---|
| A：原版系統移植 | 剩餘可達單人功能、物品效果與核准玩法；維持來源證據 |
| M：模組化架構 | 依賴、前端、路由、測試架構、共用介面；不新增玩法或調參 |
| V：獨立驗證 | 行為差分、回歸、瀏覽器、存檔、玩家驗收；不擅改正式規則 |

M0 先盤點 app.js、server.mjs、index.html、style.css、共用測試檔及進行中 PR 的重疊；共用檔案採唯一寫入責任、短批次交接。A 可繼續無衝突的移植，必要時由 M 提供介面或協調小批整合；不要求 A 全停，也不讓 M 整支重構覆蓋其他工作。

從最新正式 Web HEAD 建小分支、Draft PR，沿用既有同 HEAD push/PR 回歸、差異核對、核准範圍與逐項整合政策；合併後確認正式 HEAD/tree/CI。不得直接推正式分支、force push、擅改其他分支或合併 master。規劃紀錄本身不授權重構開始或合併。

## 6. 完成及驗收門檻

每切片提交拆分前後的來源與介面對照、涉及檔案、測試清冊、候選 SHA/tree、實際 CI、已知限制及回滾方法。

- 玩法公式、成本、獎勵、條件、機率、RNG 次序、冷卻及原版來源對照不變。
- HTTP 契約、錯誤狀態、身分／權限、重送去重、資料所有權、交易回滾不變。
- 舊 Web SQLite 正常升級／續玩，資產無遺失及重複；保存與重啟行為不變。
- 既有測試完整保留；拆分後測試發現清冊、斷言、成功與拒絕覆蓋不降低。受影響功能補必要差分、HTTP、SQLite、Chrome 及跨系統回歸，失敗不得以 skip 掩蓋。
- UI 操作、DOM 契約、繁中顯示及各視埠行為不變；新 UI 設計另行核准。
- 固定 RNG／時鐘、受控資料、Chrome 自動化與正式真人驗收分開；不冒稱真人或全功能完成。自然低機率未命中不阻擋無關移植；真正缺陷阻擋相關交付。

## 7. 暫不納入的延伸方向

資料包、擴充城鎮、選擇性啟用系統、自製 MOD、衍生遊戲可在核心契約成熟後評估；本計畫不授權相關功能，不為未知擴充需求改變原版玩法。股票、競馬、拍賣、進階住宅商業、婚姻、社交、企業等仍依現行移植清冊及來源可達性推進，不因模組化自動改變優先級。
